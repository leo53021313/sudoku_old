# 設計文件：Phase 1.5 — Fetcher Bias Fix + Empirical Generalization Test

**日期：** 2026-04-27
**類型：** Bug fix + 實驗性訓練
**狀態：** 設計完成，待 user review 後進入 writing-plans
**所屬計畫：** Phase 1.5（介於 Phase 1 與 Phase 2 之間）。Phase 1 程式 pipeline 完成但模型在 held-out 集上 0% 泛化；本期測試「修復 fetcher bias 是否就是泛化失敗的主因」。

---

## 1. 背景

Phase 1 訓練完成 2M 步、所有 milestone 通過、in-training eval 顯示 100% 全難度——但 [RESULTS.md](../../sb3/RESULTS.md) 揭露真相：

- **真隨機 / Reserved 集 eval 雙雙 0%**（400k baseline 與 2M 新 model 均如此）
- **In-training eval 是假象**：`SudokuEvalCallback` 透過 `SudokuGymEnv.reset()` → `fetch_one_puzzle_for_training()`，後者 SQL 為：

```sql
ORDER BY CASE status WHEN 'new' THEN 0 ELSE 1 END,
         tries ASC, best_empty ASC, id ASC
```

`best_empty ASC` 讓「模型最接近解開的題目排最前面」——eval 等於對「自己最熟的題目」考試。

**訓練 rollout 也用同一 fetcher** → 模型自我挑選 curriculum，只看自己快會解的題，形成記憶 lookup table 而非泛化能力。

## 2. 假設（要驗證的）

> **修復 fetcher bias（讓訓練 + eval 都用真隨機抽樣），模型會被迫泛化，reserved 集成績從 0% 顯著上升。**

如果驗證成功（reserved L1 顯著 > 0%）→ root cause 確認，後續可繼續調 regularization 推高分數，再進 Phase 2。
如果驗證失敗（reserved 仍 ~0%）→ root cause 不只在 fetcher，需轉向 Layer 3 改動（dropout、augmentation、網路架構）。

## 3. 目標 / 非目標

### 3.1 目標
- **驗證假設**：執行修復後從零跑 2M 步訓練，產出可信的 reserved 集分數
- **建立誠實的 metrics**：未來訓練不再被偏差 eval 誤導
- **保留實驗乾淨度**：除「修 fetcher 周邊」外，不動其他變因

### 3.2 非目標（明確排除）
- ❌ 改 PPO HP（n_epochs / clip_range / ent_coef / target_kl 沿用 Phase 1 v2）
- ❌ 改 BC（bc_coef、`_bc_schedule` 不動）
- ❌ 改 reward 結構
- ❌ 改 curriculum 階段定義或門檻
- ❌ 改網路架構（features extractor / constraint heads / 維度）
- ❌ 改觀察空間（26 channels）
- ❌ 改 action space（729 + mask）
- ❌ 加 dropout / data augmentation（留待 Phase 1.6 如有需要）
- ❌ 預設成功門檻（D mode：先試試看）

## 4. Layer 1 — 核心修復

### 4.1 修 `fetch_one_puzzle_for_training` SQL

**檔案：** `sb3/app/data/pool_db.py:341-392`

**改動：** ORDER BY 改為「`new` 優先 → 同類別內隨機」

```sql
-- 舊：偏差排序
ORDER BY CASE status WHEN 'new' THEN 0 ELSE 1 END,
         tries ASC, best_empty ASC, id ASC

-- 新：保留「new 優先」，內部隨機
ORDER BY CASE status WHEN 'new' THEN 0 ELSE 1 END,
         RANDOM()
```

**保留「new 優先」的理由：** 還沒被任何 worker 看過的 'new' 題目應該優先消化（給模型多樣化曝光），但同 status 內必須隨機，避免「`tries ASC` + `best_empty ASC`」造成的舒適圈偏差。

**Lock semantics 不變：** CLAUDE.md 第 24 行記載「`locked_by`/`locked_at`：Informational only；fetcher 是用 status 不是 lock state」。改 ORDER BY 不影響並行 worker 安全性。

**測試：**
- 連續呼叫 `fetch_one_puzzle_for_training(level=1)` 100 次（同一 status 池下），檢查回傳的 `id` 不是嚴格遞增 / 不是 `best_empty` 嚴格遞增 → 確認 RANDOM() 生效
- 確認 status 仍從 'new' 優先抽取

### 4.2 修 `SudokuEvalCallback` — 改用 `fetch_random_puzzles`

**檔案：** `sb3/app/rl/curriculum/eval_callback.py`

**改動：** Eval 不再透過 `env.reset()`（會走 fetch_one_puzzle_for_training），改成預先 fetch 一批 puzzle 再用 `options={board, solution}` 餵入 reset。

```python
# eval_callback.py 中現有的 _on_step 替換
for diff in self._difficulties:
    # OLD: self._eval_env.set_difficulty_distribution({diff: 1.0})
    # OLD:    obs, _ = self._eval_env.reset()
    
    # NEW: 直接從 DB 隨機抽
    db = PuzzlePoolDB(self._db_path)
    rows = db.fetch_random_puzzles(level=diff, n=self._n_episodes)
    
    for row in rows:
        board = np.array(PuzzlePoolDB.string_to_board(row["puzzle"]), dtype=np.int8)
        sol = solve(board)
        if sol is None:
            continue  # skip unsolvable
        obs, _ = self._eval_env.reset(options={
            "board": board,
            "solution": sol,
            "difficulty": diff,
        })
        # ... 後續 step loop 不變
```

**為什麼不只靠 4.1：** 雖然 4.1 修好後訓練 fetcher 也是隨機的，但 eval 仍應該獨立——不該影響 training puzzle 的 lock state（雖然 lock 是 informational，但 status 變更會發生，eval 不該改變訓練池狀態）。`fetch_random_puzzles` 是 read-only。

### 4.3 新增 `ReservedEvalCallback`

**新檔：** `sb3/app/rl/curriculum/reserved_eval_callback.py`

**功能：** 每 50k 步對 `sb3/data/eval_puzzles.json`（10 puzzles × 4 difficulties = 40 題）跑 deterministic eval，記錄 `eval/reserved_L1..L4` 與 `eval/reserved_overall` 到 TensorBoard。**不 abort**，純觀察。

**獨立 file 不共用 `SudokuEvalCallback` 的理由：** 兩者語意不同（一個是抽樣 eval，一個是 held-out gate），分離可讓未來 Phase 1.6 或 Phase 2 各自演進，不會互相牽動。Step loop 邏輯有少量複製，可接受。

**為什麼這個 callback 必要：** 即使 4.2 修好了 random eval，random eval 仍從訓練池抽，**理論上模型可能透過特定方式部分記憶**。Reserved set 是嚴格 held-out（`eval_puzzles.json` 在訓練前就已建立），是「真正沒看過的題目」。

**實作要點：**
- 重用 `EvalPuzzleSet.get_puzzles(difficulty)` 載入
- 與 `SudokuEvalCallback` 共用 step loop 邏輯（可考慮抽出 helper）
- 為了速度，跑 deterministic（`model.predict(deterministic=True)`），約 10 秒/eval

### 4.4 加 `weight_decay=1e-4`

**檔案：** `sb3/train_sb3.py`（PPO 構造處）

**改動：** `policy_kwargs` 加入 `optimizer_kwargs={"weight_decay": 1e-4}`

```python
policy_kwargs = dict(
    features_extractor_class=SudokuFeaturesExtractor,
    features_extractor_kwargs={"features_dim": 192},
    net_arch={"pi": [], "vf": [128]},
    optimizer_kwargs={"weight_decay": 1e-4},   # NEW: L2 regularization
)
```

**為什麼這個值：** 1e-4 是 PyTorch / SB3 社群常見的「無痛」起點，輕度抑制模型過度依賴特定 pattern；不會明顯影響收斂速度。

## 5. Layer 2 — Milestone 調整（防誤殺）

### 5.1 問題

Phase 1 的 `MILESTONES` 是針對「偏差訓練曲線」設計的：
- 300k：`success_rate_L1 ≥ 0.75`
- 500k：`success_rate_L1 ≥ 0.70 AND success_rate_L2 ≥ 0.50`
- 1M（warn-only）：`success_rate_L1 ≥ 0.80 AND L2 ≥ 0.70 AND L3 ≥ 0.50`
- 2M：`L1, L2, L3 ≥ 0.80 AND L4 ≥ 0.30`

修 fetcher 後，**訓練 rollout 的 success rate 會大幅下降**（因為模型不再從舒適圈抽題），上面這些 milestone 幾乎必觸發 abort。

### 5.2 改動

**保留：100k milestone（PPO 健康檢查）**
- 與訓練資料分布無關，仍有效作為「PPO 沒爆炸」的早期警告

**改為 warn-only：300k / 500k / 1M / 2M（success-rate 類）**
- 不 abort，只 log 一次「目前指標 = X，目標 Y」
- 改動：在 `MILESTONES` 各 entry 加 `"warn_only": True`

**檔案：** `sb3/app/rl/curriculum/milestone_callback.py`

```python
MILESTONES: list[dict[str, Any]] = [
    # 100k 不變（PPO health, abort if fail）
    {
        "step":            100_000,
        "approx_kl_max":   0.05,
        "entropy_min":     -2.0,
    },
    # 以下 4 個全部改為 warn_only（不 abort）
    {"step": 300_000, "success_L1_min": 0.75, "warn_only": True},
    {"step": 500_000, "success_L1_min": 0.70, "success_L2_min": 0.50, "warn_only": True},
    {"step": 1_000_000, "success_L1_min": 0.80, "success_L2_min": 0.70, "success_L3_min": 0.50, "warn_only": True},
    {"step": 2_000_000, "success_L1_min": 0.80, "success_L2_min": 0.80, "success_L3_min": 0.80, "success_L4_min": 0.30, "warn_only": True},
]
```

**結果：** 訓練不會因為 success rate 不達標而中途 abort；只有 100k PPO 真的崩了才 abort。最終結果由 reserved 集數據判斷，不靠這些 milestone。

|---|---|---|

| `train/entropy_loss` | 不該太快變 0（exploration） | > -0.3（entropy < 0.3） → entropy collapse |

### 7.2 決策樹（看 reserved L1 結果）

```
reserved L1 ≥ 50%  →  假設成功，模型確實有泛化
                       下一步：brainstorm Phase 2（inference-time search）

reserved L1 30-50%  →  假設部分成立，泛化但不夠
                        下一步：brainstorm Phase 1.6（加 dropout / data augmentation）

reserved L1 10-30%  →  fetcher 修了有幫助但不夠
                        下一步：可能要改網路架構，或把 reward shaping 重做

reserved L1 0-10%   →  假設失敗，fetcher 不是主因
                        下一步：徹底重新檢視——可能是 obs encoding、teacher 訊號、
                              或 forward-inference 架構本身的天花板
```
